# /daily-seo — ежедневная SEO-фабрика BIORISE

Один запуск = один рабочий цикл контент-фабрики. Никакого GitHub Actions, никакой автопубликации — всё выполняется прямо сейчас, в этой сессии, и останавливается перед git push, ожидая моего подтверждения.

Ключи уже лежат в `ai-seo-pipeline/.env` (Wordstat, GSC service account, PageSpeed, OpenAI) — читай их оттуда, в чат не выводи.

## Порядок действий

### 0. Ориентация

1. Прочитай `article-planner/data/daily-seo-state.json` — узнай `runsCompleted`, чтобы выбрать темп:
   - `runsCompleted < rampThreshold` (10) → режим разгона: **2–3 статьи** за прогон, вперемешку по темам (не обязательно строго ядро/вспомогательные).
   - `runsCompleted >= rampThreshold` → **4 статьи по основным услугам** (Капельницы, Анализы, Чек-апы, ЭКГ) + **1–2 по вспомогательным** (капельницы на дому, БАДы, массажи, эпиляция, биоимпеданс, справки).
2. Прочитай `article-planner/data/articles.json` (очередь) и `article-planner/data/semantic-map.json` (частотность, дожим-пометки, конфликты).
3. Пропусти в выборе тем всё, что помечено `status: "on-hold"` или уже `"published"`.

### 1. Выбор тем на сегодня

1. Из `articles.json` возьми свободные темы (`published: false`, статус `idea`/`brief`), отсортированные по `priority` (высокий → средний → низкий) и, если есть данные, по `wordstatDemand` из `semantic-map.json` (выше — приоритетнее).
2. Если тем на сегодня не хватает — открой `article-planner/data/content-map.json` (резерв, там сотни тем без проверенной частотности) и **сначала прогони кандидата через Wordstat** (см. `article-planner/collect-semantics.mjs` — используй ту же логику запроса к `https://searchapi.api.cloud.yandex.net/v2/wordstat/topRequests`) прежде чем ставить его в план на сегодня. Не пиши статью по непроверенной теме.
3. Перед тем как писать текст — **забронируй тему**: проставь ей `status: "reserved"` в `articles.json`, сверься по `semantic-map.json`, что её ключевые слова не заняты другой активной темой (см. поле `conflictsWith`).
4. Если и очередь, и резерв пусты по разумным темам — переключись на **дожим**: возьми одну из пометок «ДОЖИМ» в `notes` уже опубликованных статей (проставлены в `articles.json` после сбора семантики) и доработай её вместо новой статьи.
5. Покажи мне короткий план на сегодня (список тем с ключами и объёмом Wordstat) перед тем как писать — одной репликой, без остановки на подтверждение.

### 2. Автор

Для каждой статьи назначь реального врача клиники из `lib/authors.ts` (никаких вымышленных персон):

| Тематика | authorId |
|---|---|
| Чек-апы, анализы, ОРВИ, отравление, стресс, энергия, общие темы | `potemkina` (терапевт) |
| Диабет, щитовидная железа, гормональные темы | `boboeva` (эндокринолог) |
| Похудение, детокс, антивозрастные капельницы (Золушка, глутатион) | `tregubova` (диетолог) |
| Эстетика, кожа (бархатная кожа и т.п.) | `malofeeva` (косметолог-эстетист) |
| Массаж (аппаратный, ручной, антицеллюлитный) | `zakharov` (косметик-эстетист по уходу за телом, массажист) |
| Всё остальное | `potemkina` по умолчанию |

Проставь `authorId` в объекте статьи в `lib/articles.ts` — байлайн и Person JSON-LD подхватятся автоматически (см. `app/articles/[slug]/page.tsx`, `lib/structured-data.ts`).

### 3. Текст статьи

Пиши строго по `articles.md` (SEO title, H1, description, структура H2/H3, FAQ, вывод, CTA) и по брифу конкретной темы из `articles.json`/`content-map.json` (sections, secondaryKeywords).

Обязательно:
- **H1 не по шаблону.** Не бери H1 из `articles.json`/`content-map.json` не глядя — часть старых брифов там механически завёрнута в одну формулу «Когда [контекст] врач может обсуждать капельницу X» (нашли и почистили 11 из 37 совпадений 2026-08-07). H1 = title статьи или его лёгкая живая вариация, без единого шаблона-обёртки на все темы. Перед тем как писать текст, проверь H1 последних 3–5 уже написанных сегодня/недавно статей — если видишь повтор конструкции, переформулируй.
- **Внутренние ссылки**: 3–4 на статью, минимум одна — на страницу основной услуги (`/kapelnicy/...`, `/analizy/...`, `/chek-apy/`, `/ekg/`), вписана в тематические слова естественной фразой (никаких «тут», «здесь», «подробнее»). Остальные — на смежные статьи или анализы.
- **CTA** — обычным абзацем, никогда не оформляй как H2/H3 (ломает иерархию заголовков и вредит SEO).
- **FAQ** — 3–6 вопросов, если тема того требует; блок должен парситься `extractFaqItems` (сохраняй формат, как в уже опубликованных статьях).
- **Slug** — латиница, нижний регистр, через дефис. Проверь, что не дублирует существующий.
- Добавь новый объект в массив `articles` в `lib/articles.ts` (по образцу соседних статей): slug, title, seoTitle, h1, description, imageAlt, coverImage, authorId, excerpt, publishedAt (сегодняшняя дата), tags, content.

### 4. Проверка на слоп

Прогони готовый текст через правила скилла `stop-slop`:
- Ищи и убирай длинное тире «—» и другие AI-tell паттерны (списки видов «не просто X, а Y», канцелярит, обороты-паразиты).
- Убедись, что нет пассивного залога без действующего лица, нет расплывчатых превосходных степеней.
- Это обязательный шаг, не опциональный — не переходи к сборке, пока текст не прошёл проверку.

### 5. Картинки

Через OpenAI Images API (`OPENAI_API_KEY` из `.env`, модель `gpt-image-1`):
- 1 обложка (`coverImage`) на статью, при необходимости 1 иллюстрация в тексте.
- Стиль: спокойный, чистый, медицинский — без «вау-дизайна» (см. пример из этого же чата: капельница на светлом фоне, мягкий свет).
- Сохрани как `.webp` в `public/articles/<slug>/`, пропиши осмысленный `alt` (не «картинка 1»).
- quality: `low` или `medium` — этого достаточно для блога, экономит бюджет.

### 6. Тех-чек-лист (по каждой новой/изменённой статье)

- [ ] Canonical self-referencing — уже автоматический через `[slug]/page.tsx`, не трогать вручную.
- [ ] URL латиницей, нижний регистр.
- [ ] Title — частотный ключ ближе к началу; description до 250 символов.
- [ ] FAQ размечается в JSON-LD автоматически через `extractFaqItems` — проверь, что формат вопросов совпадает с существующими статьями.
- [ ] Автор проставлен (`authorId`), не общий «Медицинская редакция».
- [ ] Внутренняя ссылка на основную услугу есть и не задублирована.
- [ ] Хлебные крошки — автоматические через `Breadcrumbs`, ничего доп. не требуется.

### 7. Сборка и локальная проверка

```
npm run build
```

Должно быть зелёным (генерирует kapelnicy/analyses JSON + `next build`, `output: 'export'`). Если красное — чини, не показывай мне статью с падающей сборкой.

### 8. СТОП — подтверждение публикации

**Не коммить и не пушь автоматически.** Покажи мне:
- Список написанных статей (заголовок, slug, автор, ключевые слова, объём Wordstat).
- Что помечено как дожим, если делал дожим вместо новой статьи.
- Результат `npm run build`.
- Превью картинок (через Read, чтобы я увидел).

Жди явного «ок, публикуй» / «пушь» от меня. Если попросят правки — правь и показывай заново, не пушь до явного согласия.

### 9. После подтверждения

1. `git add`, `git commit` (внятное сообщение, по одной статье или пачкой — как в истории проекта), `git push` (Vercel задеплоит сам).
2. Обнови `article-planner/data/articles.json`: `status: "published"`, `published: true`, `updatedAt`.
3. Обнови `article-planner/data/semantic-map.json` (необязательно пересобирать целиком — можно точечно проставить `status: "published"` у соответствующего кластера).
4. Пингани IndexNow новыми URL:
   ```
   node scripts/submit-indexnow.js https://biorise-clinic.ru/articles/<slug1>/ https://biorise-clinic.ru/articles/<slug2>/
   ```
5. Дай список тех же URL одной репликой — я вручную закину их в «Запросить индексирование» в Google Search Console (авточерез API это не делается, см. главу про индексацию).
6. Обнови `article-planner/data/daily-seo-state.json`: `runsCompleted += 1`, `lastRunAt`, и если это первый запуск — `firstRunAt`.

### 10. Итоговый отчёт

Коротко, живым языком: что вышло, что в дожиме, что попало в резерв на завтра, есть ли технические находки (например, если по ходу заметил проблему в тех-аудите — сообщи, не чини сам без запроса).
